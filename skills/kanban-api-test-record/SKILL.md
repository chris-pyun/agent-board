# 칸반 API 검증·테스트 기록

변경에 영향을 받는 API 계약을 실제 실행으로 확인하고, 기대값과 관찰한 결과를 구분한 Markdown 기록을 남긴다. 이 Skill을 만드는 작업 자체는 API 구현이나 테스트 실행 요청이 아니다.

## 입력과 범위 확인

- 입력은 프로젝트 경로, 변경 범위 또는 검증 대상, 실행 환경이다. Git 저장소나 diff가 없어도 변경 파일 및 사용자 설명을 사용한다.
- 프로젝트의 `AGENTS.md`, `docs/design.md`, 현재 API 타입·라우트와 `package.json`을 확인한다. 현재 계약을 기준으로 하고 문서와 코드가 다르면 불일치를 기록한다. 코드의 실제 응답을 기대값으로 바꿔 테스트를 통과시키지 않는다.
- 기존 테스트와 실행 명령이 있으면 재사용한다. 없는 명령, 환경변수, DB 경로 주입 기능을 만들어낸 것으로 보고하지 않는다.
- 서버가 아직 구현되지 않았으면 검증 계획과 차단 사유만 기록한다. 테스트 준비를 이유로 다음 구현 단계까지 진행하지 않는다.

## 격리된 실행

1. 실제 사용자 DB인 `data/kanban.sqlite`는 테스트에 사용하지 않는다. 실행마다 새 임시 디렉터리에 파일 기반 SQLite를 준비한다. 인메모리 DB만으로 재시작 영속성을 검증하지 않는다.
2. 구현이 지원하는 설정 또는 테스트용 app 생성 함수를 이용해 임시 DB를 연결한다. 초기화 및 SQL 실행 전 실제 연결 경로를 확인한다. 안전하게 경로를 주입할 방법이 없으면 변경 테스트를 중단하고 해당 항목을 `BLOCKED`로 기록한다.
3. 테스트 인스턴스는 루프백과 사용 가능한 별도 포트에서 실행한다. 실행 중인 사용자의 서버나 데이터를 재사용하지 않는다. 기존 서버의 읽기 전용 관찰은 요청된 경우 별도로 표시한다.
4. 사례별 데이터와 조회한 ID·버전을 사용한다. 샘플 태스크의 고정 ID나 시작 상태에 의존하지 않는다.
5. HTTP 요청과 SSE 대기는 유한한 타임아웃을 둔다. 직접 실행한 서버와 SSE 연결만 종료한다. 임시 데이터의 정리 대상은 생성한 절대 경로를 확인하고, 실패 증거를 보존할 필요가 있으면 경로를 기록한다.

## 검증 항목 선택

변경에 관련된 항목만 선택한다. 통합 검증이나 전체 API 검증 요청에는 아래 구현된 항목을 모두 포함한다. 아직 미구현인 항목은 제외 사유를 남긴다.

| 대상 | 확인할 동작 |
| --- | --- |
| 태스크 생성·조회 | 제목 필수, 기본 Backlog, 생성 시 다섯 상태 선택 가능, 선택 필드, 에이전트 참조, 최신 생성순, 응답 계약 |
| 입력·오류 | 빈 제목·잘못된 타입·알 수 없는 필드·잘못된 상태 400, 존재하지 않는 유효 ID 404, `{error:{code,message}}` 형식 |
| 상태 전이 | `backlog → todo → in_progress → review → done`만 허용; 건너뛰기·역방향·Done 이후 이동 409 |
| UI와 에이전트 경로 | UI의 `in_progress → review`는 403, 에이전트 경로는 성공; 미배정 태스크도 에이전트 경로 사용 가능 |
| 버전·중복 | 오래된 `expectedVersion`은 409; 같은 버전의 동시 요청 중 하나만 성공; 현재 버전으로 현재 상태 재요청 시 갱신·이력·이벤트 없음 |
| 이력·원자성 | 정상 변경마다 상태·버전·이력 함께 반영; 실패 요청은 모두 변경 없음; 생성 시 가짜 변경 이력 없음; 변경 주체 미저장 |
| 에이전트 관리 | 등록·수정·미배정 삭제, 중복 이름 409, 배정된 에이전트 삭제 409, 이름·아이콘 변경이 태스크 조회에 반영 |
| 영속성·시드 | 동일 임시 DB로 테스트 서버 재시작 후 태스크·이력 유지; 최초 샘플 5개·에이전트 3개; 재시작 후 중복 시드 없음 |
| SSE | 연결을 연 뒤 변경하여 `tasks-changed` 또는 `agents-changed` 수신; 이벤트 수신 후 조회에 커밋된 결과 존재; 실패·무변경 요청은 이벤트 없음 |

- 동시 변경 검증은 동일 태스크와 동일 조회 버전을 사용한다. 성공 후 버전 증가 및 이력 추가가 각각 한 번인지 확인한다.
- 잘못된 요청 이후 상태·버전·이력을 재조회한다. 단순 HTTP 코드 확인을 트랜잭션 롤백 입증으로 표현하지 않는다. DB 실패 주입을 수행했다면 실제 방법과 관찰 결과를 별도로 기록한다.
- SSE 검증은 실제 스트림을 소비한다. 이벤트 부재 검사는 명시한 관찰 시간 내 결과로 표현한다. 재연결 후 UI 재조회와 버튼 비활성화는 화면 검사 대상이며 API 검증만으로 통과 처리하지 않는다.
- 샘플 제거 후 재시드 방지 검증이 필요하면 별도 임시 DB에만 수행한다. 태스크 삭제 API가 없다는 이유로 제품에 새 API를 추가하지 않는다.

## 결과물

프로젝트의 `docs/test-records/`에 `YYYY-MM-DD-HHmm-kanban-api.md`를 작성한다. 같은 이름이 있으면 접미사를 붙여 이전 기록을 보존한다. 시간대는 명시하고, 이 프로젝트에서는 Asia/Seoul을 사용한다. 테스트 스크립트는 반복 검증에 필요한 경우에만 추가한다.

기록에는 다음 내용을 포함한다.

- 검증 시각·시간대, 대상 변경/파일, 사용한 계약 문서, OS·Node.js·패키지 관리자 버전.
- 테스트 명령과 작업 디렉터리, DB 주입 방식과 확인한 임시 DB 경로, 테스트 주소. 비밀값은 제거한다.
- 사례별 ID, 기대값, 실제 HTTP 코드·핵심 응답·DB/SSE 관찰, 판정, 증거 위치.
- `PASS`(실행하고 기대와 일치), `FAIL`(실행하고 불일치), `BLOCKED`(필수 조건 부족), `NOT RUN`(실행하지 않음)을 구분한다. 각 판정 수와 제외한 범위를 요약한다.
- 실패에는 최소 재현 명령 또는 절차, 원인 확인 여부, 다음 조치를 남긴다. 수정 전·후 결과가 있으면 둘 다 구분해 보존한다.

표 형식 예시:

| ID | 사례 | 기대값 | 실제 관찰 | 판정 | 증거 |
| --- | --- | --- | --- | --- | --- |
| API-01 | 제목 누락 생성 | 400, 태스크 증가 없음 | 실행 시 채움 | NOT RUN | 실행 시 로그 경로 |

명령의 종료 코드가 0이라는 이유만으로 개별 기능을 통과 처리하지 않는다. 작성한 기록을 읽어 증거와 판정이 일치하는지 확인한 뒤, 사용자에게 기록 경로와 주요 결과·미검증 범위를 짧게 전달한다. 실패를 발견해도 코드 리뷰나 제품 수정으로 자동 확장하지 않으며, 수정이 이미 요청된 작업이라면 수정 후 관련 검증을 다시 실행한다.
